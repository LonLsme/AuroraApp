# 监视悬浮窗：设计取舍与遗留项（2026-08-29）

> [!note] 已归档
> 本文是 2026-08-29 对监视悬浮窗实现的一次梳理，**只记录 Aurora 自己的取舍与已知差距**。
> 现状与窗口清单见 [`../subsystems/MONITOR.md`](../subsystems/MONITOR.md)。

---

## 一、当时的取舍

| 维度 | 做法 | 理由 |
| --- | --- | --- |
| 窗口挂载 | 6 个窗口各自 `addView` 到 `WindowManager`，不放同一个容器 | 每个窗可独立开关、独立拖动；单个挂载失败不影响其余窗口（`addView` 失败会自行清理并返回 false） |
| 刷新循环 | 单线程串行采样，主线程只做数据替换 | 采样是纯文件 IO，放主线程会让拖动掉帧；串行避免 root 会话并发 |
| 拖动 | `ACTION_MOVE` 里改 `params` + `updateViewLayout`，松手才落盘 | 移动过程不产生任何写盘，拖动跟手 |
| 数据采集 | `/proc/stat` 两次采样取差值算负载；进程/线程窗降到 2000ms 一采 | 遍历 `/proc/*/stat` 开销大，降频比做增量解析更划算 |
| 状态持久化 | 只存「开关状态」与「折叠/展开状态」 | 窗口坐标每次 `show()` 重置为 `x=16dp, y=(90 + ordinal*56)dp`，按类型纵向错开 |

## 二、已知差距（用户可感知）

1. **窗口位置不持久化** —— 拖到哪儿，下次打开还是默认位置，每次重启都要重新拖。
2. **刘海屏未处理** —— 没有设置 `layoutInDisplayCutoutMode`，窗口贴边时可能被挖孔区挡住。
3. **电池电流未上窗** —— `PowerMonitor` 已能读到电流，但迷你窗/负载窗没有展示这一行。

## 三、后续可以做的（按性价比排序）

**1. 窗口位置持久化（高优先，约 20~30 行）**
`OverlayConfig` 增加 `setPosition/getPosition`，`OverlayWindow` 拖动松手时保存、`show()` 时读取。
key 必须带 `MonitorType`，六个窗口各自记录，否则会互相覆盖。

**2. 刘海适配（高优先，3 行）**
```java
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.P) {
    params.layoutInDisplayCutoutMode =
        WindowManager.LayoutParams.LAYOUT_IN_DISPLAY_CUTOUT_MODE_SHORT_EDGES;
}
```

**3. 悬浮窗补电池电流（中优先）**
`BatteryManager.BATTERY_PROPERTY_CURRENT_NOW` 在不同机型上单位不同（有的 µA、有的 mA），
需要按机型做一次可配置的单位换算，不能直接当 mA 显示。

**4. 保持进程/线程窗的 2000ms 降频（已有）**
不要为了「看起来实时」把它调回 1000ms —— 遍历进程表的开销会体现在拖动帧率上。

## 四、不要反向对齐的做法

- 用静态字段持有 `View`（会泄漏 Activity/Context）
- 每个窗口一条自己的定时器线程（6 个窗口 6 条线程，改成一条串行队列更稳）
- 拖动 `MOVE` 过程中高频 `updateViewLayout` 之外再做额外重绘
