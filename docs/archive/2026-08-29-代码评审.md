## 一句话结论

**这是一个"功能完成度远超工程质量"的项目。** 玩机功能铺得很满、中文注释写得极认真，但工程骨架停在"能跑就行"的阶段：Root 执行没有统一层、1995 行的 God Activity、零测试、release 未混淆。它现在是一个好用的个人工具，要变成能长期维护的开源项目，需要先补一轮工程化。

## 二、做得好的地方

这些不是客套，是真实的优势，改造时要保住：

1. **中文 Javadoc 注释密度罕见地高。** `OverlayPermission`、`MonitorOverlayService`、`SelinuxShellUtil` 等类的文档注释把"为什么这么做"讲清楚了，比如悬浮窗权限为什么要跳设置页、前台服务为什么用 `specialUse`。这在同类玩机工具里极少见。

2. **悬浮窗监控模块设计得相当干净。** `MonitorOverlayService` 只做命令转发 + 前台保活，`OverlayWindowManager` 管生命周期，6 个具体窗口各自独立，职责边界清晰——这是全项目分层最合理的一块，可以当作其他模块的范本。

3. **Root 检测覆盖面广。** `RootDetector` 15 类检测 + `HardcodedSignals` 特征库 + `AdvancedRuntimeDetector`，从 su 二进制、挂载点、`/proc/self/maps`、zygisk 环境变量到 Build 字段一致性，维度很全。

4. **GPL 合规做得到位。** LICENSE 保留 GPL-3.0、README 明确标注上游 violet_Box 及协议、主动移除了上游的作者可控更新检查（commit `db24e1e`）。二次开发的法律边界处理得很干净。

5. **版本目录已经用起来了。** `gradle/libs.versions.toml` 覆盖了大部分依赖，只是没覆盖全（见问题 9）。

## 三、问题清单

### P0 — 影响稳定性/安全，建议优先修

**1. Android 14+ 前台服务崩溃隐患** — ✅ **已修复（2026-08-29）**

`MonitorOverlayService.java:106` 调用的是两参数的 `startForeground(id, notification)`，而 Manifest 中已声明 `android:foregroundServiceType="specialUse"`。targetSdk 34+ 时，若 Manifest 声明了 type 却不调用带 type 的三参重载，系统会在 API 34+ 设备上抛 `MissingForegroundServiceTypeException`。

修复方式：新增 `startForegroundCompat()`，按 `SDK_INT` 分流调用，并加 `try-catch` 兜底应对定制 ROM。

**1b. 顺带修复：startForegroundService 调用契约缺失** — ✅ **已修复（2026-08-29）**

排查时发现同一段代码里的第二个崩溃源。原逻辑为「无窗口则直接 `stopSelf()`」：

```java
if (manager.runningCount() > 0) {
    startForeground(NOTIFICATION_ID, buildNotification(...));
} else {
    stopForeground(STOP_FOREGROUND_REMOVE);
    stopSelf();          // ← 从未调用过 startForeground()
}
```

本服务由 `startForegroundService()` 启动，Android 8+ 要求在超时前调用 `startForeground()`，否则抛 `RemoteServiceException`（API 31+ 为 `ForegroundServiceDidNotStartInTimeException`）。触发场景：`ACTION_STOP_ALL` 冷启动服务且窗口数为 0 时直接 `stopSelf()`，进程被杀。

修复方式：无论后续是否停止，先挂一次通知满足系统契约，再走收尾流程（通知随即被移除，用户无感知）。

**修复验证**

- 单独编译 `MonitorOverlayService.java` 通过（javac + SDK 36.1 + androidx.core），零错误
- 反编译字节码确认分流正确：`SDK_INT >= 34` → `startForeground(I,Notification,I)`；`< 34` → `startForeground(I,Notification)`
- `ServiceInfo.FOREGROUND_SERVICE_TYPE_SPECIAL_USE`（1073741824）被 javac 内联为立即数，低版本设备不会 `NoSuchFieldError`

> 注：完整 `assembleDebug` 未能跑通，原因是本机 Android Studio 正持有 `E:\DEV\.gradle` 的锁（wrapper 无法创建 `.lck`）。这是环境冲突，与代码无关——关闭 AS 后在你的终端执行 `./gradlew assembleDebug` 即可。建议在 Android 14+ 真机上开一次悬浮窗做最终确认。

**2. Root 执行层完全缺失，10 处 su 调用散在 6 个类**

```
SelinuxShellUtil.java        2 处
ModuleBackupActivity.java    4 处
ModuleManagerActivity.java   2 处
FontLibraryBackupActivity.java / MainActivity.java
PartitionManagerActivity.java 各 1 处
```

每处超时都不一样（1200ms / 1500ms / 3000ms / 25000ms），错误处理方式各异，`MainActivity` 里甚至存在三套并行实现（`runSuCommand` / `execSuCapture` / `executeQuickRebootCommand`）。后果是：行为不一致、无法统一加超时和重试、改一处要改六处。

建议抽 `com.aurora.app.core.root.RootShell`：单例维护 root shell 会话（或直接接入 libsu，README 里已经声称用了 libsu，实际没有），统一超时/线程调度/结果封装。

**3. Shell 命令拼接存在注入面**

`MainActivity` 里已经写好了 `shellEscape()`（第 583 行），说明作者意识到了这个问题，但只有部分调用点使用。反例：

- `ModuleBackupActivity.java:170` — `new ProcessBuilder("su", "-c", "mkdir -p \"" + backupDir + "\"")`
- `ModuleBackupActivity.java:295 / 320` — 拼接整段 wrapper/move 脚本
- `RootDetector.java:133 / 180 / 196 / 215 / 355` — `Runtime.getRuntime().exec("cat " + path)`

本项目路径多来自内部常量，实际利用门槛高；但备份目录、模块名等一旦开放用户输入，就是 root 权限下的命令注入。建议：所有外部输入一律走 `shellEscape()`，或改用 `ProcessBuilder` 数组传参避免经过 shell 解析。

**4. 主线程执行 shell 的风险**

`CpuCoreMonitor.java`、`CpuSysFiles.java`、`RootDetector.java` 中直接 `Runtime.getRuntime().exec(...)`。如果这些类被 UI 线程调用（`/proc/mounts`、`/proc/self/maps` 行数可达数千），会造成 ANR。`SelinuxShellUtil` 的注释里写了"带超时避免主线程误用时卡死"，说明这个坑已经被踩过一次。建议：采集类 API 强制异步（返回 `Future` 或走回调），同步方法加 `@WorkerThread` 注解。

**5. release 构建不可用 + 体积偏大**

`app/build.gradle.kts` 中 `isMinifyEnabled = false`，且没有 `signingConfigs`。意味着现在只能产出 debug 包，18 MB 的体积里有大量可剔除的 Compose/Material 未使用代码。建议开启 `isMinifyEnabled = true` + `isShrinkResources = true`，签名配置从 `local.properties` 或环境变量读取 keystore 信息（不入库）。

### P1 — 架构与可维护性

**6. `MainActivity` 1995 行的 God Activity**

同时承担：底部导航、4 个 Tab 内容渲染、Root 检测调度、状态栏脚本、快捷重启、模块自动安装、日志读写、悬浮窗控制。全项目 261 次 `findViewById`（`buildFeatures` 只开了 `compose`，没开 `viewBinding`）。

建议按 Tab 拆 Fragment，把 Root 检测、模块安装抽成独立 UseCase 类。开 `viewBinding = true` 可以一次性消掉 261 处 `findViewById` 和随之而来的空指针防御代码。

**7. 没有生命周期感知的架构组件**

无 ViewModel / LiveData / Repository / DI。横竖屏切换会重建 Activity 并重新触发整套 Root 检测（十几次 shell 调用），且 `exploreAutoInstallTriggered` 这类标志位只能靠 `volatile` 字段手动兜。建议至少引入 ViewModel + `repeatOnLifecycle`，把检测状态从 Activity 里搬出来。

**8. 国际化几乎为零**

`values/strings.xml` 只有 1 条 `app_name`，而 Java/Compose 中存在 **755 处硬编码中文字符串**（`MainActivity` 独占 121 处）。目前是纯中文应用，无所谓；但只要想支持英文，就得先做一次大规模抽取。

**9. 依赖版本管理分裂**

`libs.versions.toml` 覆盖了 AndroidX 系列，但 okhttp / commons-compress / xz / commons-io / rootbeer 五个依赖直接把版本硬编码在 `app/build.gradle.kts` 里。升级时要同时看两个地方。建议全部收进版本目录。

**10. README 与实现不一致**

- README 技术栈写"libsu"，实际依赖里没有
- README 功能列表里的"Play 完整性检测"，代码中只有 `RootDetector` 里作为关键词字符串出现，没有对应实现

对外开源后这类不一致会直接产生 issue。建议同步修正。

**11. 核心 UI 依赖冷门第三方库**

`backdrop` + `capsule`（`io.github.kyant0`）承载了整个液态玻璃底部导航（510 行 Compose 的核心）。这两个库社区使用率低、维护状态不明，且是视觉核心。建议评估：能否把关键效果（blur / lens / ContinuousCapsule）自行实现并 vendor 进项目，或者至少锁定版本 + 在 README 标注上游风险。

**12. 零有效测试**

`app/src/test` 和 `androidTest` 各有一个 AS 模板测试文件。而 `RootDetector` 的 15 类检测、`shellEscape()`、`PayloadCore`、各 Monitor 的解析逻辑，全都是纯函数、极易单测——这是投入产出比最高的一块空白。

### P2 — 清理项

13. **`jadx.zip`（1.8 MB）入库。** 反编译工具打包进 Git，既占体积，作为 GPL 上游的二次开发产物也容易引发授权层面的质疑。建议移出仓库或改 Git LFS。`tools/` 下 6 张图标 PNG 合计约 2.1 MB，同样建议。

14. **`app/src/main/cpp/` 是死代码。** 有 `CMakeLists.txt` 和 `native-lib.cpp`，但 `build.gradle.kts` 里没有任何 `externalNativeBuild` 配置——永远不会被编译。`app/src/main/proto/` 是空目录。两者建议删除。

15. **`build_first.log` 应删除。** 内容是一次 wrapper 构建失败（Gradle 缓存目录锁权限问题），属排查残留。

16. **权限核查。** `READ_PHONE_STATE` 在代码中未见使用；`QUERY_ALL_PACKAGES` 已加 `tools:ignore`，但上架 Play 需申报。建议清理未使用权限。

17. **`catch (Exception ignored)` 出现 80 处。** 其中 Root 相关路径上的静默失败会直接表现为"点了没反应"，用户无从判断是没 root 还是命令失败。建议至少打 `Log` 或给用户可见的错误反馈。

## 五、最后

这个项目的功能直觉和注释习惯都很扎实——尤其悬浮窗监控那块的分层，看得出是有设计意识的。当前的主要矛盾不是"写得差"，而是**功能推进速度超过了架构演进速度**，欠下的工程债集中在 Root 执行层和 MainActivity 两处。

建议优先级：**先修 P0-1 的崩溃隐患，再抽 RootShell**。这两步做完，项目的可维护性会有肉眼可见的提升，后面拆 Activity、补测试都会顺很多。
