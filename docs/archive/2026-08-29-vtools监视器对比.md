## 一句话结论

**Aurora 的架构明显更现代，vtools 的细节更经得起用。** Aurora 赢在分层、保活、拖动流畅度和刷新策略；vtools 赢在窗口位置记忆、刘海屏适配和指标丰富度。有意思的是——两边 CPU 负载的采集原理完全一致，都是读 `/proc/stat` 做两次采样的差值。

## 一、代码地图

### vtools

监视器在 `app/src/main/java/com/omarea/vtools/popup/`，共 4 个窗口类：

| 文件 | 行数 | 职责 |
|------|------|------|
| `FloatMonitor.kt` | 436 | 主监视器：CPU / GPU / 温度 / 电池 |
| `FloatMonitorMini.kt` | 263 | 单行胶囊简化版 |
| `FloatMonitorThreads.kt` | 135 | 线程数监视 |
| `FloatFpsWatch.kt` | 238 | 帧率与单帧耗时 |

配套：
- UI 组件 `ui/`：`FloatMonitorChartView.kt`(211)、`FloatMonitorBatteryView.kt`(218)、`FloatProcessAdapter.kt`(230)
- 配置弹窗 `dialogs/DialogMonitor.kt`(94)
- **数据采集 `library/shell/`：23 个工具类** —— `CpuLoadUtils`、`CpuFrequencyUtils`、`GpuUtils`、`FpsUtils`、`BatteryUtils`、`MemoryUtils`、`ProcessUtils`、`ThermalControlUtils`、`SwapUtils`、`LMKUtils` 等

### Aurora

监视器在 `ui/overlay/`，6 种类型（枚举 `MonitorType`）：

`LOAD` 负载 · `PROCESS` 进程 · `THREAD` 线程 · `MINI` 迷你 · `FPS` 帧率 · `TEMPERATURE` 温度

分层：`MonitorOverlayService`(164) → `OverlayWindowManager`(116) → `OverlayWindow`(366 抽象基类) → 6 个实现

采集层：`core/monitor/` 10 个 Monitor + `core/util/` 6 个工具类，共 16 个。

## 二、逐维度对比

| 维度 | vtools | Aurora | 更优 |
|------|--------|--------|------|
| **后台保活** | 无 Service，纯 `WindowManager.addView` | 前台服务 `specialUse` + Manager 托管 | **Aurora** |
| **刷新调度** | `Timer` + `TimerTask`（每窗口一个线程） | `Handler.postDelayed`（主线程消息循环） | **Aurora** |
| **采集并发** | 各窗口独立 Timer 线程，同时开多个窗口则多线程并发读 sysfs | 共享单线程 `ExecutorService` 串行采集 | **Aurora** |
| **刷新间隔** | 主窗 1500ms / Mini 1500ms / Fps 1000ms | FPS·Mini 500ms / 负载 1000ms / 进程·线程·温度 2000ms | **Aurora** |
| **拖动流畅度** | `ACTION_MOVE` 每次调 `updateViewLayout` | 拖动中只改 View translation，松手才更新一次窗口位置 | **Aurora** |
| **折叠/展开** | 切换 `LinearLayout.orientation` | 两套 View 切换 + 平滑动画 | **Aurora** |
| **代码复用** | 4 个类各自重复窗口创建、触摸、定时器逻辑 | 抽象基类统一，子类只实现采集与渲染 | **Aurora** |
| **内存泄漏** | `companion object` 静态持有 `mView`/`mWindowManager`，用 `@SuppressLint("StaticFieldLeak")` 压制 | 实例字段，由 Manager 持有，hide 时释放 | **Aurora** |
| **窗口位置记忆** | `SharedPreferences` 存 x/y，拖动后持久化 | 不保存，每次显示回到默认位置（按类型序号错开） | **vtools** |
| **刘海屏适配** | `layoutInDisplayCutoutMode = SHORT_EDGES`（API 28+） | 无 | **vtools** |
| **指标覆盖** | GPU 负载/频率/显存、电池电流 mA、RAM%、各核心负载 | 独立进程窗口、独立线程窗口、帧耗时 | **各有所长** |
| **采集层厚度** | 23 个工具类 | 16 个 | **vtools** |
| **实现语言** | Kotlin | Java（Compose 仅用于主界面导航） | **vtools** |

## 三、实现细节拆解

### 3.1 窗口挂载（两边几乎一致）

```kotlin
// vtools — FloatMonitor.kt
params.type = if (Build.VERSION.SDK_INT >= O)
    LayoutParams.TYPE_APPLICATION_OVERLAY else LayoutParams.TYPE_SYSTEM_ALERT
params.flags = FLAG_NOT_TOUCH_MODAL or FLAG_NOT_FOCUSABLE or FLAG_FULLSCREEN
if (Build.VERSION.SDK_INT >= P) {
    params.layoutInDisplayCutoutMode = LAYOUT_IN_DISPLAY_CUTOUT_MODE_SHORT_EDGES
}
```

```java
// Aurora — OverlayWindow.java
params.type = Build.VERSION.SDK_INT >= O
    ? TYPE_APPLICATION_OVERLAY : TYPE_PHONE;
params.flags = FLAG_NOT_FOCUSABLE | FLAG_NOT_TOUCH_MODAL | FLAG_LAYOUT_NO_LIMITS;
```

差异只有两点：vtools 多了刘海屏适配；Aurora 用 `FLAG_LAYOUT_NO_LIMITS` 允许窗口移出屏幕边界，vtools 用 `FLAG_FULLSCREEN`。

**Aurora 缺 `layoutInDisplayCutoutMode`**，在刘海屏/挖孔屏上窗口无法延伸到顶部区域，是个可见的小瑕疵。

### 3.2 刷新循环（Aurora 更讲究）

vtools 用 `Timer` + `TimerTask`，每 1500ms 触发一次 `updateInfo()`：在 Timer 子线程里完成**所有**采集（CPU、GPU、内存、温度、电流、FPS），然后 `myHandler.post { }` 回主线程刷 UI。

Aurora 用 `Handler.postDelayed` 自递归，采集与渲染分离得更干净：

```java
// OverlayWindow 基类约定的子类职责
protected void collectData() { }      // 后台线程：只做耗时 IO
protected void refreshContent() { }   // 主线程：只更新 UI
protected long getRefreshIntervalMs() { return 1000L; }  // 可覆写
```

并且**按数据特性分级**：FPS 和迷你窗 500ms（变化快），负载 1000ms，进程/线程/温度 2000ms（变化慢、采集成本高）。这是 vtools 没有做的优化。

另外 Aurora 用共享的**单线程** `ExecutorService` 串行化采集，避免同时开 6 个窗口时多线程并发读 sysfs 互相抢占；vtools 每个窗口一个 Timer 线程，多开时会并发抢占。

### 3.3 拖动实现（Aurora 明显更好）

```kotlin
// vtools：每次 MOVE 都触发窗口重布局
MotionEvent.ACTION_MOVE -> {
    params.x = (event.rawX - touchStartX).toInt()
    params.y = (event.rawY - touchStartY).toInt()
    mWindowManager!!.updateViewLayout(v, params)   // 高频 IPC + 重布局
}
```

`updateViewLayout` 要走一次 WindowManager 的 IPC 并触发窗口重新布局，手指每移动一像素就调一次，拖动时容易掉帧。

Aurora 的做法（见 `OverlayWindow` 类注释）：

> 拖动期间用 View translation 跟手（GPU 合成层移动，不触发窗口重布局），松手才一次性更新窗口位置

手指移动时只改 View 的 translation 属性——纯渲染层变换，不经过 WindowManager；松手时才 `updateViewLayout` 提交最终位置。这是标准的悬浮窗拖动优化写法，vtools 没做。

### 3.4 数据采集（原理相同，厚度不同）

两边 CPU 负载算法完全一致：读 `/proc/stat`，取两次采样的 `total` 与 `idle` 差值计算占用率。

```java
// vtools — CpuLoadUtils.java
lastCpuState = KernelProrp.INSTANCE.getProp("/proc/stat", "^cpu");
// 按核心索引解析，计算各核负载
```

Aurora 在 `core/util/CpuStatReader.java` + `CpuSysFiles.java` 中做同样的事。

差异在**覆盖广度**：vtools 的 `library/shell/` 有 23 个采集类，包含 GPU 负载/频率/显存（`GpuUtils`）、电池电流（`BatteryManager.BATTERY_PROPERTY_CURRENT_NOW`）、交换分区、LMK 等；Aurora 16 个，覆盖 CPU/内存/电池/温度/FPS/进程/线程/GPU，但**悬浮窗里没有展示电池电流**。

### 3.5 状态持久化（vtools 更完整）

```kotlin
// vtools：拖动结束后保存坐标
monitorStorage.edit().putInt("x", params.x).putInt("y", params.y).apply()
```

Aurora 的 `OverlayConfig` 只持久化两样：开关状态、折叠/展开状态。窗口坐标每次 `show()` 都重置为 `x=16dp, y=(90 + type.ordinal()*56)dp`——按类型序号纵向错开排列。

**这是用户能直接感知的差距**：vtools 拖到哪儿下次打开还在哪儿，Aurora 每次重启都要重新拖。

## 四、指标覆盖对照

| 指标 | vtools | Aurora |
|------|--------|--------|
| CPU 总负载 | 图表 + 百分比 | 负载窗（3 个仪表环） |
| CPU 频率 | 各簇频率 + 每核负载 | 采集层有，悬浮窗未重点展示 |
| GPU 负载/频率 | 图表 + MHz | 有 `GpuMonitor`/`GpuInfoQuery` |
| GPU 显存 | 有 | 无 |
| 温度 | 图表 + °C | 独立温度窗（电池 + CPU） |
| 电池电量 | 有 + 充电图标 | 有 |
| 电池电流 | 有（mA 实时） | 有 `PowerMonitor`，悬浮窗未展示 |
| RAM 使用率 | 有（展开后） | 有 `MemoryMonitor` |
| FPS | 有 | 独立帧率窗（含单帧耗时） |
| 进程 | 任务管理器（独立悬浮窗） | 独立进程窗（CPU 占用 Top N） |
| 线程数 | 有 | 独立线程窗 |

## 五、给 Aurora 的落地建议

按性价比排序，前两项都是几十行内的改动：

**1. 窗口位置持久化（高优先，用户可感知）**
在 `OverlayConfig` 增加 `setPosition/getPosition`，`OverlayWindow` 拖动松手时保存，`show()` 时读取。约 20–30 行。
注意 key 要带 `MonitorType`，六个窗口各自记录位置。

**2. 刘海屏适配（高优先，3 行）**
```java
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.P) {
    params.layoutInDisplayCutoutMode =
        WindowManager.LayoutParams.LAYOUT_IN_DISPLAY_CUTOUT_MODE_SHORT_EDGES;
}
```

**3. 悬浮窗补电池电流（中优先）**
`PowerMonitor` / `core/util/BatterySysFiles` 已有采集能力，在迷你窗或负载窗展开态补一行 mA 显示即可。参考 vtools 用 `BatteryManager.BATTERY_PROPERTY_CURRENT_NOW`，注意不同机型单位不同（vtools 用 `SpfConfig.GLOBAL_SPF_CURRENT_NOW_UNIT` 做了可配置的单位换算，这个设计值得照搬）。

**4. 进程/线程窗口的采集降频（已有，保持）**
Aurora 设的 2000ms 是对的——读 `/proc/*/stat` 遍历进程开销不小，vtools 的任务管理器没做这种区分。

**5. 不必借鉴的部分**
vtools 的静态字段持有 View（`StaticFieldLeak`）、每窗口一个 Timer 线程、MOVE 时高频 `updateViewLayout`——这三处 Aurora 已经做得更好，不要反向对齐。
